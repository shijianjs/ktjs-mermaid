# 设计说明

声明怎么组织、哪些是生成的、wrapper 在哪里刻意不再精确。

## 按领域分文件

| 文件 | 内容 |
| --- | --- |
| `Mermaid.kt` | 入口接口 `Mermaid`、`mermaid` 访问器、`MermaidAPI`、`Diagram` |
| `MermaidDefault.kt` | `@JsModule("mermaid")` 的 default 导入 |
| `MermaidTypes.kt` | `RunOptions`、`RenderResult`、`ParseOptions`、`ParseResult`、`DetailedError`、`UnknownDiagramError`、`InitNodes`、`parseOrNull` |
| `DiagramApi.kt` | 图型定义相关契约：`DiagramDB`、`DiagramRenderer`、`ParserDefinition`、`DiagramDefinition`、`ExternalDiagramDefinition`、`DiagramOrientation`，以及 d3 选择集的句柄 |
| `Icons.kt` | Iconify JSON 结构与两种图标加载器 |
| `Layouts.kt` | `LayoutAlgorithm`、`LayoutLoaderDefinition`、`RenderOptions`、`LayoutData`、`InternalHelpers` |
| `config/ConfigTypes.kt` | 生成的 `MermaidConfig` 树 |

划分跟着上游的声明文件走：类型待在拥有它的功能旁边，`DiagramRenderer` 不会埋在一份讲入口的文件里。

## 配置树是生成出来的

`MermaidConfig` 有 36 个接口、572 个成员。手抄一份的话，上游一个 minor 版本就能让它失真，所以
`scripts/generate-config.py` 读 `node_modules/mermaid/dist/config.type.d.ts`，产出
`config/ConfigTypes.kt`：

```bash
./gradlew kotlinNpmInstall          # 让 mermaid 的声明出现在 node_modules 下
python scripts/generate-config.py    # 重写 ConfigTypes.kt
```

生成器不是一个通用的 TypeScript 声明解析器：它只认识这个文件里出现的写法（`interface`、`extends`、
内联对象字面量、`Partial<…>`、字符串/数字字面量联合、`Record<K,V>`），遇到别的结构会直接报错停下。
它产出：

- 接口 → `external interface`，继承关系照搬上游；
- 内联对象字面量 → 提成 `<Owner><Field>` 命名的接口；
- `string | number` → 共用的 `StringOrDouble`；
- 字符串字面量联合 → `sealed external interface` + 一个 `(String)` 工厂 + `Xs` 常量对象，
  每个上游字面量一个 `inline val`；
- 字面量联合里混着类型（`boolean | ('arc' | 'gap')`）→ 普通 `external interface`，每支一个工厂，
  外加常量对象；
- 子接口重声明了继承来的成员 → 标 `override`；类型不一致时成员改名 `typed<Name>` 并用
  `@JsName` 映射回原属性名。

产物带 `Generated by` 文件头。手改会在下次生成时丢掉：改脚本，或者把例外记进
[coverage.md](https://github.com/shijianjs/ktjs-mermaid/blob/main/docs/development/coverage.md)。

## 哪些是不透明的，为什么

有些上游类型描述的是没人会手写的结构，或者是 Kotlin/JS 无法直接建模的 d3 辅助层。它们留成
`external interface` 句柄，这样函数签名依然诚实：

| 类型 | 为什么是句柄 |
| --- | --- |
| `LayoutData` | 自定义布局收到的图数据，上游描述有数百行，而布局实现只是原样传回去 |
| `InternalHelpers` | 上游标了 deprecated 且是内部的（"definitions will change without notice"）；`InternalHelpers.helper(name)` 取单个 helper |
| `SVG`、`SVGGroup`、`HTML` | d3 选择集，kotlin-wrappers 不建模 d3 |
| `StyleClasses` | 上游是 `Map<string, DiagramStyleClassDef>`，而 kotlin-wrappers 的 `JsMap` 把键约束成 `JsAny?`，Kotlin 的 `String` 键满足不了；用 `StyleClasses.styleClass(id)` 读单个条目 |

## 两个值得记下来的上游坑

- **default 导出。** mermaid 入口只有一个 `default` 导出。给模块命名空间写 `external object`
  会编译成**具名**导入（`import { MermaidModule } from "mermaid"`），webpack 在打包时直接报错；
  用带 `@JsName("default")` 的顶层 `external val` 才会生成 default 导入。整个模块只声明一个这样的值。
- **容器不能和图共用 id。** `mermaid.render(id, text, container)` 会用 `id` 在文档里找它的 svg。
  如果传入的容器本身已经带着这个 id，mermaid 量到的就是容器而不是 svg，渲染会死在
  `svg.node(...)?.getBBox is not a function`。

## 测试

模块的测试跑在 Chromium 里，因为一张图只有被量过、排过版才算真的画出来。每个用例都真的调用库：
渲染进容器并把结果插进 DOM、解析合法与非法文本、检测图型、在 `initialize` 之后读回配置、
覆盖字面量联合、通过 `mermaidAPI` 拿到 `Diagram`。字面量常量逐条对照上游字符串，所以重新生成的
配置文件不会悄悄漂移。

公开面的覆盖情况、以及哪些是刻意不包的，都记在 [coverage.md](https://github.com/shijianjs/ktjs-mermaid/blob/main/docs/development/coverage.md)。
